# Field Dispatch Messaging: SMS API Sender Compliance and Registration Evidence

A field technician can miss an appointment when an SMS stalls, while finance can act on the wrong numbers when a generated report never arrives. The operational constraint is evidence, not API convenience: every dispatch alert and every attached report needs a durable identity, a lawful sending route, and a status trail that survives retries.

**Short answer:** choose an SMS integration only after proving that it supports the sender-registration path for each destination country, signed status callbacks, stable message identifiers, and exportable event history. Put it behind a small channel adapter. For the related email report, generate MIME correctly, authenticate the sending domain, retain a digest of the exact attachment, and treat provider acceptance as an intermediate state rather than proof that a person received or read it.

The simple approach is one API call followed by `sent = true`. It is attractive during a startup sprint and wrong for this job. Record intent before network I/O, separate provider acceptance from later delivery events, and tolerate duplicate or out-of-order callbacks.

## How should a field dispatch app evaluate SMS alerts API sender registration?

An HTTP success usually establishes a narrow fact: the provider accepted a request and assigned an identifier. SMS delivery can still fail farther downstream. Email can be accepted by one system and rejected, quarantined, or filtered later. A dispatch screen that collapses those states into a green check makes uncertainty look like certainty.

Use a compact state model. `queued` means the application durably recorded the intent. `accepted` means the provider accepted it. `delivered` is a provider-reported terminal event. `failed` needs a normalized reason plus untouched provider detail. `unknown` is a real outcome when no trustworthy terminal event arrives before the business deadline. It must not silently become `delivered`.

Unknown is data.

This distinction matters. An SMS marked delivered is evidence about a network status report, not evidence that the technician read it. An email event is not evidence that finance opened the attachment. Human acknowledgement, when the workflow needs it, belongs in the application as a separate event.

## Make identity and consent deployment inputs

There is no single global sender-ID switch. In the United States, application-to-person traffic over 10-digit long codes uses an A2P 10DLC registration process covering brands and campaigns; the cited implementation documentation distinguishes that route from toll-free and short-code traffic. European requirements are not one uniform sender-ID product either. The ePrivacy Directive sets rules for unsolicited direct marketing, while national implementation and carrier rules determine practical registration details. GDPR principles such as purpose limitation and data minimization apply when phone numbers and delivery logs identify people.

So country is configuration, not a string prefix. Before launch, keep a destination matrix containing the approved sender type, registration owner, permitted use case, consent or other lawful basis, opt-out behavior, quiet-hours policy where applicable, and escalation channel. Legal review must resolve the jurisdiction-specific parts. An SDK cannot.

Do not let a fallback route change identity without an explicit policy decision. Substituting a number or alphanumeric sender may alter replies, opt-out handling, registration scope, and the recipient's ability to recognize the message. Reliability includes predictable identity.

No shortcut fixes that.

The email side has a parallel constraint. Google documents SPF or DKIM requirements for all senders to personal Gmail accounts and additional SPF, DKIM, DMARC, alignment, and unsubscribe requirements for bulk senders. Build the attachment as MIME, set a stable `Message-ID`, and avoid putting sensitive report data in the subject or status logs.

## Record one evidence trail across both channels

The record should join the business event to channel attempts without pretending the channels have identical semantics. For a work order, keep an internal notification ID, recipient reference, consent snapshot, template version, destination jurisdiction, provider message ID, state transitions, and timestamps. For the financial report, add the report period, MIME message ID, attachment media type, byte length, and a SHA-256 digest of the generated bytes. The digest establishes which artifact was sent without copying report contents into observability systems.

Keep payload retention narrow. Phone numbers, email addresses, message bodies, and reports can all be sensitive. Operational logs generally need pseudonymous recipient references and normalized outcomes, while controlled systems hold the destination and document. Retention should follow the business and legal purpose rather than the lifetime of the company.

One invariant pays for itself: a business notification can have several attempts, but each provider event attaches to exactly one attempt. That makes retries auditable and stops a late callback for attempt one from overwriting attempt two.

Retries are normal.

## A focused TypeScript boundary

This boundary makes the provider replaceable, but the larger payoff is testability: production code and a fake adapter must produce the same normalized shapes.

```ts
type Channel = "sms" | "email";
type DeliveryState = "accepted" | "delivered" | "failed" | "unknown";

type SendCommand = {
  notificationId: string;
  attemptId: string;
  channel: Channel;
  destination: string;
  content: string;
  attachment?: {
    filename: string;
    mediaType: "application/pdf";
    bytes: Uint8Array;
  };
};

type AcceptedReceipt = {
  attemptId: string;
  providerMessageId: string;
  acceptedAt: string;
};

type DeliveryEvent = {
  providerMessageId: string;
  state: DeliveryState;
  occurredAt: string;
  reason?: string;
};

interface DeliveryAdapter {
  send(command: SendCommand): Promise<AcceptedReceipt>;
  verifyAndParseCallback(
    rawBody: Uint8Array,
    headers: Readonly<Record<string, string | undefined>>
  ): Promise<DeliveryEvent>;
}

async function dispatch(
  command: SendCommand,
  adapter: DeliveryAdapter,
  store: {
    createQueuedAttempt(command: SendCommand): Promise<void>;
    markAccepted(receipt: AcceptedReceipt): Promise<void>;
  }
): Promise<void> {
  await store.createQueuedAttempt(command);
  const receipt = await adapter.send(command);
  await store.markAccepted(receipt);
}
```

Persisting before `send` closes one gap: a process crash cannot erase the intent. It creates another. A timeout can leave the caller unsure whether the provider accepted the request. Use a provider-supported idempotency mechanism when available; otherwise reconcile before retrying, and show uncertainty instead of guessing.

The trade-off is extra state and a reconciliation worker in exchange for an honest account of ambiguous sends. I would accept that operational cost before hiding uncertainty behind a boolean, because a duplicate dispatch alert and a missing alert can both change what happens in the field.

Verify callback signatures against raw request bytes before parsing, reject invalid callbacks, retain the original event identifier when one exists, and make application idempotent. Never assume arrival order. A delayed `accepted` event must not move an attempt backward from `delivered`; an event for an unknown message ID belongs in reconciliation rather than the trash.

## The shortcut that fails under retry

Sending the SMS inside the database transaction that creates the work order is tempting. The database can roll back after the external send succeeds, leaving a real message with no local record. Committing first and sending second can strand unsent work after a crash.

Use a transactional outbox when the dispatch record and notification intent share a database. Commit both together, then let a worker claim and send the row. This provides at-least-once processing, so deduplication remains necessary. It does not create exactly-once delivery.

For report email, generation should be deterministic for a fixed report version. Freeze the accounting snapshot, produce the PDF, calculate its digest, and enqueue the attempt. If a retry regenerates changing bytes under the same report ID, the audit trail becomes ambiguous. Reuse the stored artifact or create a new version.

Keep SMS content operational: identify the service organization, state the dispatch action, and provide a reply or application path appropriate to the registered use case. Keep confidential account values out of the alert. The attachment can carry more detail, but access control, retention, and recipient verification should match its sensitivity.

## Measure this before copying the design

Start with a country-by-country launch test, not a generic sandbox success. Verify registration lead time and renewal ownership, supported sender types, reply behavior, opt-out processing, callback authentication, event export, documented rate limits, and escalation procedures. Exercise invalid numbers, carrier rejection, duplicate callbacks, callbacks arriving out of order, worker crashes after acceptance, and an attachment near your own configured limit.

Then measure separate clocks: queue age, provider-accept latency, time to terminal status, percentage still unknown at the dispatch deadline, duplicate-attempt rate, and reconciliation backlog. Break results down by country, route, and channel without placing personal data in metric labels. For email, track generation failures and attachment size distributions; a functioning mail API cannot deliver a PDF that never finished rendering.

Cost belongs in the decision, but it follows reliability constraints. Model registration work, support burden, engineering time for callback normalization, retained-event storage, and the cost of missed appointments or delayed reconciliation. A nominal message price is a weak comparison when a route cannot lawfully or predictably serve the destination.

Ship the narrowest route matrix that covers the first real markets. Add countries only after identity, consent, testing, and monitoring are explicit. The rule is blunt: if an integration cannot produce trustworthy evidence from queued intent through terminal channel status, it is not ready for dispatch or financial-report workflows.

Start there.
